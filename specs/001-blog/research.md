# Research: 한채 블로그 플랫폼 기술 결정

**Feature**: `001-blog` | **Date**: 2026-10-07 | **Plan**: [plan.md](./plan.md)

`/speckit.plan` Phase 0 결과다. 민주가 정한 조건은 **프론트엔드 HTML·CSS·JavaScript, 백엔드 Python** 두 가지이고, 나머지는 아래 추천안으로 정했다. 각 항목은 결정 → 이유 → 검토한 대안 순서로 적는다.

선택 기준은 세 가지다.

1. **처음 만드는 사람이 끝까지 갈 수 있는가.** 민주 개인 명세 1.5의 "처음 다루기 쉬운 것으로 선택"을 따른다. 직접 만들어야 하는 부품이 적을수록 좋다.
2. **스펙의 보안·정합성 요구를 기본 기능으로 채우는가.** XSS(FR-116, SC-010), CSRF(FR-116), 권한(FR-110, SC-004), 중복 요청(FR-117, SC-005)을 손으로 다 짜지 않아도 되는 쪽을 고른다.
3. **팀 문서와 어긋나지 않는가.** 팀 ERD 파트 분담 컨벤션은 MySQL이다(`docs/ERD_파트2_글분류검색.md`).

## 1. 백엔드 프레임워크

- **Decision**: **Django 5.2 LTS** (Python 3.13)
- **Rationale**:
  - 화면을 서버에서 HTML로 만들어 보내는 방식(템플릿)이 기본이라, "HTML·CSS·JS + Python" 조합에 그대로 맞는다. 별도 프론트엔드 프레임워크나 빌드 도구가 필요 없다.
  - 회원·세션·비밀번호 해시, ORM과 마이그레이션, 폼 검증, 페이지 나누기, 관리 도구가 들어 있다.
  - 템플릿이 기본으로 HTML을 이스케이프하고(FR-116), CSRF 방어가 기본으로 켜져 있다(FR-116).
  - 5.2는 장기 지원(LTS) 버전으로 2028년 4월까지 보안 패치가 나온다. 아래 django-allauth 등 주요 라이브러리가 지원한다.
- **Alternatives considered**:
  - **Flask**: 가볍고 배우기 쉽지만 회원, ORM, 마이그레이션, CSRF, 폼 검증을 각각 확장으로 붙여야 한다. 이 스펙 규모(FR 80여 개)에서는 붙일 부품이 너무 많다.
  - **FastAPI**: JSON API 중심이라 화면을 JS로 따로 그려야 한다(SPA). 화면 수(20개 이상)만큼 프론트엔드 일이 커지고, 로그인 세션·CSRF·XSS를 직접 챙겨야 한다.
  - **Django 6.0**: 최신이지만 LTS가 아니고 지원 기간이 짧다. 내장 CSP 같은 새 기능은 5.2에서 django-csp로 대신할 수 있다.

## 2. 프론트엔드 방식

- **Decision**: **Django 템플릿(서버 렌더링) + 순수 CSS + 순수 JavaScript(ES 모듈)**. 빌드 도구·CSS 프레임워크 없음.
- **Rationale**:
  - 모든 화면이 JS 없이도 열리고, 공감·구독·댓글·이미지 업로드처럼 새로고침 없이 반응해야 하는 부분만 JS의 `fetch`로 처리한다.
  - 주소마다 서버가 완성된 HTML을 주므로 새로고침·공유·뒤로 가기가 그대로 동작한다(FR-070 "결과에도 주소가 있어").
  - 모바일 우선 CSS(360px부터) + 넓은 화면 미디어 쿼리로 SC-008을 맞춘다. 좁은 화면 사이드바는 `<dialog>` 서랍 메뉴로 연다(FR-118).
- **Alternatives considered**:
  - **React·Vue SPA**: 민주가 정한 스택(순수 HTML·CSS·JS)에서 벗어나고 빌드 과정이 생긴다.
  - **htmx**: 서버 렌더링과 잘 맞지만 JS를 직접 쓰겠다는 선택과 겹치고 배울 것이 하나 늘어난다. 구현 중 반복이 많아지면 다시 검토한다.
  - **Bootstrap·Tailwind**: 한옥 테마 등 서비스 개성을 디자인 단계에서 정하기로 했으므로(spec Assumptions) 처음부터 디자인 언어를 묶지 않는다.

## 3. 데이터베이스

- **Decision**: **MySQL 8.4 LTS** (문자셋 `utf8mb4`, 정렬 `utf8mb4_0900_ai_ci`)
- **Rationale**:
  - 팀 ERD 컨벤션과 민주의 파트 2 DDL(`docs/erd_part2.sql`)이 MySQL 기준이라 그대로 옮겨 쓸 수 있다.
  - 내장 **ngram 전문 검색**으로 한국어 부분 일치 검색과 정확도순 정렬(FR-071)을 별도 검색 엔진 없이 할 수 있다.
  - `utf8mb4_0900_ai_ci`는 영문 대소문자를 구분하지 않으므로 FR-070 "대소문자 구분 없음"이 DB 기본 동작으로 맞는다.
  - 8.0은 2026년 4월에 지원이 끝났으므로 장기 지원판인 8.4를 쓴다. Django 5.2가 지원한다.
- **Alternatives considered**:
  - **SQLite**: 설치가 없어 가장 쉽지만 한국어 전문 검색이 약하고, 정각 집계 작업과 웹 요청이 동시에 쓸 때 잠금 문제가 생긴다. 개발용으로만 쓰면 운영과 검색 동작이 달라진다.
  - **PostgreSQL**: 기능은 더 풍부하지만(부분 유니크 인덱스, pg_trgm) 팀 컨벤션과 다르고, 한국어 검색을 위해 확장 설정이 필요하다.

## 4. 회원·인증 (이메일 + 카카오·구글·네이버)

- **Decision**: **django-allauth** (65.x 이상). 이메일 가입·인증·비밀번호 재설정과 카카오·구글·네이버 소셜 로그인을 한 라이브러리로 처리한다. 비밀번호 해시는 **Argon2**(`argon2-cffi`).
- **Rationale**:
  - 세 소셜 제공사(kakao, google, naver)를 모두 기본 지원한다.
  - 이메일 인증 필수(FR-001a), 일회용·시간 제한 재설정 링크(FR-001c), 로그인 실패 시 이메일·비밀번호 구분 없는 안내(FR-001b), 로그인 후 원래 화면 복귀(FR-002, `next` 파라미터), 로그인 시도 횟수 제한을 설정으로 켤 수 있다.
  - "같은 이메일의 소셜 계정은 새로 가입시키지 않고 기존 방식으로 안내"(FR-001d)는 allauth 어댑터의 `pre_social_login`에서 이메일이 이미 있는 계정이면 가입을 멈추고 안내 문구와 함께 로그인 화면으로 돌려보내는 방식으로 구현한다.
- **Alternatives considered**:
  - **Django 기본 auth + 제공사별 OAuth 직접 구현**: 제공사 세 곳의 인증 흐름·토큰·예외 처리를 직접 짜야 한다. 보안 실수 위험이 크다.
  - **Authlib**: 범용 OAuth 클라이언트라 가입·이메일 인증·재설정 화면은 직접 만들어야 한다.
- **주의할 점** (구현 전에 확인):
  - **카카오**: 이메일 동의 항목은 비즈 앱(개인 개발자 비즈 앱 포함)에서만 받을 수 있다. 이메일을 못 받으면 그 회원은 이메일 없이 가입되고 FR-001d 검사는 건너뛴다.
  - **네이버**: 개발 중에는 등록한 테스트 계정만 로그인할 수 있고, 공개 서비스로 쓰려면 검수를 받아야 한다.
  - 세 제공사 모두 콜백 주소(`/accounts/{provider}/login/callback/`)를 개발용·운영용으로 각각 등록해야 한다.

## 5. WYSIWYG 에디터

- **Decision**: **Quill 2** (BSD 라이선스). 빌드 없이 `static/vendor/quill/`에 넣어 쓴다. 저장 형식은 **HTML**.
- **Rationale**:
  - FR-022가 요구하는 문단 제목·굵게·기울임·글자색·정렬·목록·인용·코드 블록·링크·이미지를 기본 툴바로 모두 지원한다.
  - 이미지 버튼을 가로채 서버 업로드 API(`POST /api/images`)로 올리고 받은 주소를 커서 위치에 넣을 수 있다(FR-029). 여러 장은 고른 순서대로 차례로 올려 넣는다.
  - 라이선스 키가 필요 없고 상업 이용 제약이 없다.
- **Alternatives considered**:
  - **TinyMCE 7·CKEditor 5**: 기능은 더 많지만 최신판은 GPL 또는 상용 라이선스이고 라이선스 키 설정이 필요하다.
  - **Toast UI Editor**: 한국에서 많이 쓰였지만 마크다운 중심이고 최근 유지보수가 거의 없다.
  - **Tiptap**: 확장성이 좋지만 npm 빌드가 사실상 필요하다.
- **서버 쪽 정리(필수)**: 에디터가 보낸 HTML은 저장 전에 **nh3**로 허용 목록 방식 정리를 한다(FR-116, SC-010). 허용 태그는 `p h2 h3 strong em u s span a ol ul li blockquote pre code img br`, 허용 속성은 `a[href]`(http·https만, `rel="noopener noreferrer nofollow"` 강제), `img[src]`(우리 서비스 이미지 주소만), `class`(`ql-align-*`, `ql-syntax`만), `style`(`color`, `background-color`만)이다. 같은 단계에서 검색·요약용 순수 텍스트(`content_text`)를 만든다.

## 6. 이미지 업로드

- **Decision**: **Pillow**로 실제 이미지인지 열어 확인하고, 파일당 **10MB** 상한(통합본 '자율' 값). 저장소는 서버 디스크(`MEDIA_ROOT`), 웹 서버(Caddy)가 직접 내려준다.
- **Rationale**:
  - 확장자·MIME만 믿지 않고 Pillow로 열어 형식이 jpg·png·gif·webp인지 확인해 위장 파일을 거절한다(FR-114).
  - JPEG만 EXIF 방향을 반영해 다시 저장하고(휴대폰 사진 방향), GIF·PNG·WEBP는 원본 그대로 저장해 GIF 움직임을 지킨다.
  - 파일 이름은 서버가 만든 무작위 이름(UUID)을 쓴다.
- **Alternatives considered**:
  - **S3 같은 객체 저장소(django-storages)**: 서버가 여러 대가 되거나 디스크가 부족할 때로 미룬다. 저장 위치는 설정 하나로 바꿀 수 있게 Django storage API만 쓴다.

## 7. 정각 집계와 예약 작업

- **Decision**: Django **관리 명령**(`manage.py compute_rankings`, `manage.py publish_scheduled_posts`)을 서버 **cron**이 실행한다. 순위 집계는 매시 0분, 예약 발행(P3)은 1분마다.
- **Rationale**:
  - 집계 로직이 웹 앱 코드 안에 있어 테스트하기 쉽고, 별도 작업 서버(Celery, Redis)가 필요 없다.
  - 순위 스냅숏은 `(종류, 기준 시각)`에 유일 제약을 걸어, 같은 정각에 두 번 돌아도 한 번만 저장된다.
  - 정각 직후 5분 안 갱신(SC-006)은 0분 실행 + 수 초 집계로 충분하다.
- **Alternatives considered**:
  - **Celery + Redis**: 기능은 강력하지만 서비스가 두 개 늘어난다. 지금 규모에는 과하다.
  - **APScheduler를 웹 프로세스 안에서 실행**: 웹 프로세스가 여러 개면 중복 실행되고, 재시작하면 일정이 꼬인다.
- 이용 제한 기한 만료(FR-102)는 작업 없이 요청 때마다 `ends_at`과 현재 시각을 비교해 판단한다.

## 8. 조회수 중복 방지

- **Decision**: 같은 **방문자 키**가 같은 글을 **30분** 안에 다시 열면 세지 않는다. 방문자 키는 회원이면 회원 ID, 비회원이면 서명된 무작위 쿠키(1년)의 값이다. 쿠키가 없는 요청(봇 등)은 IP와 User-Agent의 해시로 대신한다.
- **Rationale**: Clarifications "짧은 시간 안에 다시 연 글은 세지 않는다"의 "짧은 시간"을 30분으로 정했다. 1시간 순위 창보다 짧아야 정상 재방문이 순위에 반영된다.
- **구현**: 글 상세 요청마다 `post_views`에서 `(post_id, viewer_key, viewed_at > now-30분)`을 확인하고 없을 때만 조회 기록을 넣고 `view_count`를 1 올린다. 블로그 주인 본인의 조회도 센다(통합본에 제외 규칙이 없음).

## 9. 중복 요청 방지 (FR-117, SC-005)

- **Decision**:
  - **글 발행·댓글 등록**: 화면을 열 때 일회용 토큰(UUID)을 숨은 필드로 넣고, 같은 토큰으로 두 번 오면 처음 만든 것을 돌려준다(DB 유일 제약).
  - **공감·구독·저장**: "누르면 뒤집기"가 아니라 **원하는 상태를 보내는** API(`PUT` = 켜기, `DELETE` = 끄기)로 만든다. 연타해도 같은 상태가 반복될 뿐이다. 버튼은 요청 중 비활성화한다.
  - **수치**: 공감 수·댓글 수·구독자 수는 따로 저장하지 않고 매번 실제 행을 센다(인덱스 사용). 저장한 숫자와 실제가 어긋날 일이 없다. 조회수만 숫자 열로 둔다.
- **Alternatives considered**: 수치를 열로 두고 트랜잭션으로 함께 갱신하는 방식은 탈퇴·숨김·삭제 때 맞춰 줄 곳이 많아 어긋나기 쉽다. 성능 문제가 보이면 그때 캐시를 붙인다.

## 10. 권한과 공개 범위 판단

- **Decision**: 글을 볼 수 있는지는 **한 곳**(`posts/policy.py`)에서만 판단한다.
  - `can_view_post(post, viewer)`: FR-028 순서(존재 → 블로그 소속 → 블로그 이용 제한 → 관리자 숨김 → 주인 여부 → 공개 범위·상태) 그대로.
  - `Post.objects.visible_to(viewer)`: 같은 규칙의 쿼리셋 버전. 목록·검색·홈·순위·피드·사이드바 개수·이전/다음 글이 모두 이것만 쓴다(SC-003).
  - 화면별 권한은 데코레이터(`@login_required`, `@blog_owner_required`, `@service_admin_required`)로 걸고, FR-110 권한표의 모든 ✕ 칸을 매개변수 테스트로 확인한다(SC-004).
  - 남의 비공개 글은 403이 아니라 404(FR-111).
- **Rationale**: 공개 범위 조건이 화면마다 흩어지면 한 군데서 빠뜨리기 쉽다. SC-003은 "어디에서도 0건"이다.

## 11. 목록 페이지와 "더 불러오기"

- **Decision**:
  - 블로그 글 목록·카테고리·태그·검색 결과: **페이지 번호** 방식, 한 페이지 10개(FR-113). 마지막을 넘으면 빈 목록.
  - 홈 최신 글·주제별 글·구독 피드: **커서** 방식 "더 불러오기". 커서는 마지막 글의 `(published_at, id)`. 새 글이 위에 생겨도 중복·누락이 없다(FR-081, FR-061).
  - 정렬은 `published_at DESC, id DESC`(같은 시각이면 나중에 만든 글 위).

## 12. 테스트

- **Decision**: **pytest + pytest-django**(단위·통합), **factory_boy**(테스트 데이터), **Playwright for Python**(E2E). 코드 검사는 **ruff**.
- **Rationale**: Playwright 하나로 크로미움(크롬·엣지)과 웹킷(사파리) 엔진, 360px 화면을 모두 확인할 수 있다(SC-008, SC-009).
- 테스트 DB도 MySQL을 쓴다(전문 검색·정렬 규칙이 운영과 같아야 함).

## 13. 배포

- **Decision**: **리눅스 서버 한 대 + Docker Compose**. 구성은 `caddy`(HTTPS 자동 발급, 정적 파일·이미지 제공) → `web`(Gunicorn + Django) → `db`(MySQL 8.4). 서버 cron이 관리 명령을 실행한다. 서버는 한국 리전의 소형 VM(예: AWS Lightsail 서울, 네이버 클라우드)에 메모리 2GB 이상.
- **Rationale**: 서버 하나에 모든 것이 있어 이해하기 쉽고, 개발 환경(같은 compose 파일)과 운영 환경이 거의 같다. 정각 집계(cron)와 이미지 디스크 저장이 자연스럽게 된다.
- **Alternatives considered**:
  - **PaaS(Render, Railway, Fly.io 등)**: 배포는 쉽지만 MySQL·예약 작업·디스크를 각각 따로 구성해야 하고 비용 구조가 달라진다.
  - **쿠버네티스**: 이 규모에 과하다.
- **메일**: 운영은 SMTP 발송 서비스(예: Amazon SES), 개발은 **Mailpit**(가짜 메일함)으로 인증·재설정 메일을 확인한다.
- **백업**: 매일 `mysqldump`와 이미지 폴더를 다른 저장소로 복사한다.
