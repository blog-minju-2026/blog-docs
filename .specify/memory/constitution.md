# 한채 블로그 플랫폼 Constitution

이 문서는 한채 블로그 플랫폼을 만드는 동안 모든 단계(plan, tasks, implement)가 지켜야 할 원칙이다.
기능의 내용은 [spec.md](../../specs/001-blog/spec.md)와 기준 문서인 [통합 기능명세서](../../docs/1팀_블로그_통합_기능명세서.md) v0.2가 정하고, 이 문서는 **어떻게 만들어야 하는가**의 기준을 정한다.

## Core Principles

### I. 명세가 먼저다 (Spec-First)

- 모든 코드 변경은 spec.md의 요구사항 ID(통합본 기능 ID, 예: `POST-03`, `COM-P01`)로 거슬러 올라갈 수 있어야 한다. 커밋, PR, 작업 목록, 테스트 이름에 ID를 적는다.
- spec.md에 없는 기능은 만들지 않는다. 필요하면 먼저 spec.md를 고치고(필요하면 `/speckit.clarify`), 그다음 구현한다.
- 기능 ID는 통합본 1.4 규칙을 따른다. 번호는 영역 끝에 붙이고, 삭제된 번호는 다시 쓰지 않는다.
- 구현 중 명세와 다르게 동작해야 할 이유가 생기면 코드로 먼저 바꾸지 않고, 명세를 고친 뒤 코드를 맞춘다.

**이유**: 세 사람의 서비스를 같은 기준으로 테스트하고 비교하려면(통합본 1.1), 코드가 명세의 어느 줄을 구현했는지 언제나 찾을 수 있어야 한다.

### II. 권한은 서버가 지킨다 (NON-NEGOTIABLE)

- 모든 요청은 서버(API)에서 통합본 3.2 권한표(spec의 `COM-01`)로 검사한다. 화면 JavaScript가 버튼을 숨기거나 다른 화면으로 보내는 것은 편의일 뿐 보안이 아니다. API를 직접 불러도 같은 결과가 나와야 한다.
- 남의 비공개 글, 비공개 카테고리의 글, 예약 발행 전 글, 숨김 처리된 글은 403이 아니라 **404**로 답해 존재 자체를 숨긴다.
- 공개 범위 판단은 한곳(공통 함수나 공통 조회 조건)에서 하고, 목록·검색·홈·인기 글·피드·사이드바·글 개수가 모두 그것을 거친다. 화면마다 따로 조건을 쓰지 않는다.
- 서비스 관리자도 남의 글·댓글 내용은 수정할 수 없다. 제재는 숨김으로만 한다.

**이유**: 주소를 직접 입력하거나 요청을 직접 보내도 같은 결과가 나와야 한다(통합본 3.3, 8.1-2). 공개 범위 조건이 흩어지면 한 화면에서만 새는 사고가 생긴다.

### III. 기본이 안전하다 (Secure by Default)

- 사용자가 입력한 모든 내용은 화면에 보일 때 이스케이프한다. 화면은 JavaScript가 그리므로, 사용자 값은 `textContent`나 공통 이스케이프 함수(`escapeHTML`)를 거쳐서만 넣는다. HTML로 그대로 넣는 값은 서버가 허용 목록으로 정제해 보낸 글 본문 하나뿐이다. 어떤 화면에서도 스크립트가 실행되면 안 된다(8.1-1).
- 상태를 바꾸는 요청(쓰기, 수정, 삭제, 공감, 구독)은 CSRF 토큰으로 보호하고, GET으로 상태를 바꾸지 않는다(8.1-3).
- 비밀번호는 검증된 단방향 해시(예: Argon2, bcrypt)로만 저장한다. 비밀번호, 토큰, 세션 값은 주소, 화면, 오류 메시지, 로그에 남기지 않는다(8.1-4).
- 업로드 파일은 확장자가 아니라 내용으로 이미지인지 확인한다(4.6, 8.1-5).
- 오류 화면에 내부 정보(스택 추적, SQL, 경로)를 보여 주지 않는다(8.1-6).
- 비밀 값(DB 비밀번호, 소셜 로그인 키)은 저장소에 커밋하지 않고 환경 변수(GitHub Secrets)로 넣는다.
- 저장소가 공개이므로 자동화(GitHub Actions) 로그에 이메일 · 닉네임 같은 개인 정보를 찍지 않는다. 정기 작업은 개수만 남긴다.

**이유**: 블로그는 남이 쓴 내용을 남에게 보여 주는 서비스라 입력 처리 실수가 바로 다른 사용자의 피해로 이어진다.

### IV. 데이터는 언제나 맞는다 (Data Integrity)

- 글 발행, 댓글 등록, 공감, 구독은 연달아 보내도 한 번만 처리된다. DB 제약(유일 키 등)으로 막고, 화면의 버튼 막기는 보조로만 쓴다(8.3-1).
- 여러 단계가 함께 처리되는 작업(글 삭제, 카테고리 삭제, 블로그 이사, 회원 탈퇴)은 하나의 트랜잭션으로 처리해 일부만 반영된 상태를 남기지 않는다(8.3-4).
- 공감 수, 댓글 수, 구독자 수, 글 수는 새로고침하면 실제 값과 같아야 한다. 집계 값을 따로 저장한다면 원본과 같은 트랜잭션에서 갱신한다(8.3-2).
- 블로그 주소와 글 주소는 한 번 정해지면 바뀌지 않고, 쓴 블로그 주소는 영구히 예약된다(4.2, 4.3).
- 글, 이미지, 댓글은 서비스를 다시 시작해도 남는 저장소에 둔다(8.3-5).
- DB 구조 변경은 마이그레이션 파일로만 하고, 손으로 운영 DB를 고치지 않는다.

**이유**: 숫자가 틀리거나 반쯤 지워진 글이 남으면 사용자는 서비스를 믿지 못한다.

### V. 테스트로 확인한다

- spec.md의 수용 시나리오(Given/When/Then)마다 자동 테스트를 하나 이상 둔다. 테스트 이름이나 설명에 요구사항 ID를 적는다.
- 기능 코드와 그 테스트는 같은 PR에 들어간다. 테스트가 없는 기능 PR은 병합하지 않는다.
- 권한(원칙 II)과 공개 범위, 중복 처리(원칙 IV)는 **테스트를 먼저 쓰고** 실패를 확인한 뒤 구현한다. 비회원·회원·블로그 주인·서비스 관리자 네 상태로 권한표의 모든 ✕ 칸을 시도하는 테스트를 둔다(SC-004).
- 테스트는 로컬에서 명령 하나로 돌릴 수 있어야 하고, 병합 전에 모두 통과해야 한다.

**이유**: 성공 기준(SC-003~SC-005, SC-010)은 "0건", "100%"처럼 사람이 눈으로 확인하기 어려운 조건이라 자동 테스트로만 지킬 수 있다.

### VI. 단순하게 만든다

- 화면은 **정적 HTML 파일 + 빌드 없는 JavaScript**로 만들고, 데이터는 서버의 **JSON API**(`/api/...`, [API 명세서](../../docs/API명세서.md))로 주고받는다. 화면 파일과 API는 같은 서버 · 같은 주소에서 내보내 세션 쿠키와 CSRF가 그대로 통하게 한다.
- 화면 하나는 HTML 파일 하나와 `js/pages/{화면}.js` 하나다. API 주소는 공통 모듈(`store.js`) 한곳에만 쓰고, 요청 · CSRF · 오류 처리(`api.js`), 로그인(`auth.js`), 링크와 공통 조각(`common.js`)도 한곳에 둔다.
- 화면 프레임워크 · 번들러 · SPA 라우터를 쓰지 않는다. 주소마다 실제 HTML 파일이 있어 새로고침 · 뒤로 가기 · 주소 공유가 그대로 된다.
- JavaScript가 꺼진 브라우저는 지원하지 않는다. 대신 API가 실패하거나 화면을 그리지 못하면 빈 화면을 두지 않고 무엇이 안 됐는지와 다시 시도할 방법을 보인다.
- 새 라이브러리나 프레임워크를 들일 때는 plan.md에 이유와 대안을 적는다. 표준 라이브러리나 이미 쓰는 도구로 되면 새로 들이지 않는다.
- spec.md 우선순위대로 만든다. P1(통합본 P0)이 한 바퀴 돌기 전에 P2·P3 기능을 시작하지 않는다.
- 지금 필요하지 않은 확장 지점, 설정, 추상화를 미리 만들지 않는다.

**이유**: 혼자 만들고 유지하는 프로젝트라, 구조가 복잡해질수록 명세를 지키는 데 쓸 시간이 줄어든다. 화면과 API를 나누면 권한 · 공개 범위 · 중복 처리를 API 테스트만으로 확인할 수 있고(원칙 II · V), 디자인 시스템 「한채」의 시안을 HTML · CSS로 그대로 옮길 수 있다. 빌드 도구가 없으니 파일을 고치면 바로 배포된다.

## 기술 제약

- **화면**: HTML, CSS, JavaScript(빌드 없음, 프레임워크 없음). 화면 방식은 원칙 VI를 따른다.
- **서버**: Python. 웹 프레임워크, DB, 소셜 로그인 라이브러리, 배포 방식은 `/speckit.plan`에서 정하고 plan.md에 이유를 남긴다.
- **사용성 기준**(통합본 8.4, spec SC-008·SC-009): 360px 폭 휴대폰 화면에서 모든 P1 기능을 가로 스크롤 없이 쓸 수 있다. 최신 크롬·사파리·엣지에서 같은 결과를 낸다. 날짜와 시각은 한국 시간으로 보여 준다. 잘못된 입력은 어느 항목이 왜 틀렸는지 알리고 입력한 내용은 지우지 않는다.
- **성능 기준**(통합본 8.2, spec SC-007): 목록은 페이지 단위로 불러오고, 목록에는 작은 이미지만 쓴다. 한 화면을 그리는 데 쿼리 수가 글 개수에 비례해 늘어나지 않게 한다(N+1 금지).
- **언어**: 문서와 화면 문구는 한국어로 쓴다. 코드의 이름(변수, 함수, 테이블)은 영어로 쓴다.

## 개발 흐름

1. Spec Kit 순서를 따른다: constitution → specify → clarify → plan → tasks → (analyze) → implement. 단계는 하나씩 진행하고, 각 단계 결과는 PR로 올려 민주가 확인한 뒤 병합한다.
2. plan.md는 'Constitution Check' 절에서 원칙 I~VI를 하나씩 확인하고, 어기는 부분이 있으면 이유와 더 단순한 대안을 버린 이유를 'Complexity Tracking'에 적는다.
3. tasks.md의 각 작업은 요구사항 ID를 달고, 원칙 V에 따라 테스트 작업을 구현 작업 앞에 둔다.
4. 구현 PR은 작게 나눈다. 한 PR은 하나의 사용자 이야기나 기능 ID 묶음을 다룬다.
5. PR을 병합하기 전에 확인한다: 테스트 통과, 요구사항 ID 표기, 비밀 값 미포함, 이 문서의 원칙 위반 없음.
6. 구현하면서 화면 방식 · 구성 · 주소처럼 plan에 적은 것과 다르게 만들게 되면, 그 PR이나 바로 다음 PR에서 plan.md(필요하면 이 문서)를 함께 고친다. 문서가 코드보다 뒤처진 채로 두지 않는다.

## Governance

- 이 문서는 다른 모든 작업 방식보다 우선한다. plan, tasks, 코드가 이 문서와 어긋나면 그쪽을 고치거나, 이 문서를 먼저 개정한다.
- 개정은 PR로 하고, 맨 위 Sync Impact Report와 아래 버전을 함께 고친다.
  - **MAJOR**: 원칙을 빼거나 뜻을 거꾸로 바꿈
  - **MINOR**: 원칙이나 절을 새로 더하거나 크게 넓힘
  - **PATCH**: 문구 다듬기, 오타, 뜻이 바뀌지 않는 설명 추가
- 개정하면 이미 만든 plan.md, tasks.md가 새 원칙과 맞는지 다시 확인한다.
- 원칙에서 벗어나야 할 때는 그 PR이나 plan.md의 Complexity Tracking에 이유를 남긴다. 이유 없이 벗어난 코드는 병합하지 않는다.
